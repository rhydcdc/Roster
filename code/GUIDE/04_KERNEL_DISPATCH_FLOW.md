## 0단계 · 실제 실행 순서 한눈에 보기 (시계열 타임라인)

실제 추론이 돌아갈 때는 **모델 로드 시 1회 사전 준비**가 먼저 끝나 있고, 배치가 들어오면 한 층 안에서 아래 순서대로 CPU와 GPU가 맞물려 돌아간다.

| 순서 | 실행 주체 | 실제 하는 일 | 실제 소요 시간 (`CH2`, `d = 4,096`) | 핵심 결과 |
|:---:|---|---|---:|---|
| **사전 준비** | CPU *(모델 로드 1회)* | 고정 출석부(`32×4,096`)에서 8개 구역별 비트맵·이웃 중심점 **사전 준비 표** 생성 | **`13.1 ms`** *(딱 1회)* | 시험 데이터 `0건` · 배치 전 완료 |
| **1단계** | **GPU** *(동시)*<br>**CPU → GPU** *(동시)* | **GPU:** 이번 층 **어텐션** 실행<br>**CPU:** 어텐션 직전 입력으로 중심점 배정 → **`A3V4`** 계획 → 번호표 전송 | GPU 어텐션: **`3.24 ~ 13.30 ms`**<br>CPU+전송(1층 최악): **`1.41 ~ 2.09 ms`** | **어텐션 뒤에 완전 은폐**<br>(노출 지연 **`0.000 ms`**) |
| **2단계** | **GPU · FFN 1단계**<br>*(확장 · `gate·up`)* | 1단계 결과 표 `h` 비우기(`0.025~0.078 ms`) → **8개 구역 순으로 5단계 비격자 `gate·up` 실행** | `2.04 / 2.87 / 5.09 ms`<br>*(4층 합)* | **충돌(`atomicAdd`) `0`** · 빈칸 쓰기 생략 · 닮은 중심점 순으로 바로 저장 |
| **3단계** | **GPU · FFN 2단계**<br>*(축소 · `down`)* | 묶음별 **활성 열 압축**(`0.012 ms/층`) → **`down + 잔차`** 합산 실행 후 원래 자리로 복귀 | `1.07 / 1.78 / 3.29 ms`<br>*(4층 합)* | **충돌(`atomicAdd`) `0`** · 한 GPU 작업 팀이 한 묶음 전담 합산 |

이제 위 **1단계 → 2단계 → 3단계**를 실제 실행 순서 그대로, 3번 문서의 **토큰 6명(`T1 ~ T6`) × 뉴런 8개(`N1 ~ N8`)** 예시로 끝까지 따라가 보자.

## 1단계 · 실시간 타일 계획(`A3V4` 디스패처) & 어텐션 `0.000 ms` 중첩

3번 문서의 비격자 5단계 타일 계획은 원래 파이썬·CPU 온라인 솔버로 풀면 **`28.8 ~ 46.1초`가** 걸렸다. 실제 LLM 서버에서는 이 계획을 **몇 `ms` 안에** 끝내야 한다.

### ① 어떻게 `46초`짜리 계획을 `1.50 ~ 2.83 ms`로 `16,000배` 넘게 줄였나?

**핵심 조건:** 토큰별 예측기(`Deja Vu` 등)는 매 토큰마다 $2^{4096}$가지 중 생전 처음 보는 뉴런 패턴이 튀어나와 미리 준비할 수 없다. 반면 우리 `CH2`는 나올 수 있는 출석부가 **고정된 `32`가지(4층 `256`가지)로 완전히 닫혀 있다.** 배치마다 달라지는 것은 오직 **"32개 중심점 방에 토큰이 몇 명씩 들어왔는가"뿐**이다.

그래서 `A3V4` 디스패처는 일을 **사전 준비 표**(모델 로드 1회)와 **실시간 조립**(매 배치) 두 조각으로 나눈다.

#### 사전 준비 (모델 로드 시 딱 1번, `13.1 ms` — 배치 도착 전!)
고정된 출석부 표에 구역 벽(`N1~N4` ┃ `N5~N8`)을 미리 치고 아래 3가지를 작은 사전으로 만들어 둔다.
- **구역별 출석부 비트맵:** 각 구역 안에서 `A, B, C, D`가 어떤 뉴런을 켜는지 `1/0` 비트로 압축 보관
- **구역별 이웃 중심점 순위표:** 구역 안에서 뉴런이 많이 겹치는 짝꿍 순서 *(예: 1구역에서 `A`의 1순위 이웃 = `D`(2칸 겹침) → `B`(1칸 겹침))*
- **닮은 중심점 줄 세우기 순서(`OLO` 순서):** 가족끼리 붙어 앉도록 정한 순서 **`A → B → C → D`**

#### 매 배치 도착 시 실시간 조립 (`1.50 ~ 2.83 ms` — 소규모 예시!)
실제 서버에서는 토큰이 중심점 순서대로 얌전히 들어오지 않고 **뒤죽박죽 섞여서 도착**한다.
- **실제 도착 순서 (원래 입력 줄 번호):** `0번: T5(C)` · `1번: T1(A)` · `2번: T6(D)` · `3번: T2(A)` · `4번: T4(B)` · `5번: T3(A)`

이때 `A3V4`가 하는 일은 딱 3단계다.

| 순서 | `A3V4`가 하는 일 (소규모 6명 예시) | 실제 `CH2` 속도 비결 |
|:---:|---|---|
| **① 번호표 줄 세우기** | 무거운 벡터 데이터는 손대지 않고 **번호표만** 닮은 순서(`A→B→C→D`)로 한 번 훑어 정리:<br>**`[1번(T1), 3번(T2), 5번(T3)]` (`A`) → `[4번(T4)]` (`B`) → `[0번(T5)]` (`C`) → `[2번(T6)]` (`D`)** | 토큰 수(`B`)만큼 딱 1번 훑는 초고속 계수 정렬 |
| **② 구역별 동시 타일링** | 3번 문서 5단계처럼 **1구역(`N1~N4`)과 2구역(`N5~N8`)은 벽으로 나뉘어 100% 독립**이다.<br>CPU 일꾼들이 구역을 나눠 맡아 동시에 비격자 타일 목록을 뽑는다. | **16스레드가 `4층 × 8구역 = 32구역`을 동시 처리** + CPU 벡터 연산(`AVX2`)으로 512열 점수 동시 합산 |
| **③ 2단계 합집합 동시 생성** | 1단계 타일을 뽑는 김에, 곧바로 이어질 **2단계 묶음별 합집합 뉴런 목록**(`묶음 1 = {N1,N2,N3,N5}` 등)도 그 자리에서 함께 기록해 GPU로 전송! | 1단계 계획과 2단계 계획이 **한 번에 완성** (4층 합 `1.50 ~ 2.83 ms`, 최악 1층 `1.12 ~ 1.81 ms`) |

- **구조적 시너지:** 앞 3층 중심점을 32개로 통합한 `CH2` 구조 덕분에 전체 타일 수가 **`1,774 / 2,528 / 4,103`개**로 작게 유지되어, **사전 준비 표 `13.1 ms`**, **4층 런타임 디스패치 `1.50 ~ 2.83 ms`**, **GPU 전송 크기 `1.1 ~ 3.3 MB`까지** 한꺼번에 가벼워졌다.

### ② 어텐션 중첩 타임라인 — "어텐션이 안 끝났는데 어떻게 미리 짜나?"

랩미팅에서 가장 먼저 나오는 질문이 바로 이것이다: *"이번 층 어텐션 결과가 나와야 FFN에 들어가는데, 어텐션이 돌아가는 동안 어떻게 이번 층 FFN 타일 계획을 미리 짜나?"*

- **해답:** [02_SINGLE_INFERENCE_FLOW.md](02_SINGLE_INFERENCE_FLOW.md) 1단계에서 본 것처럼, 우리 모델은 **어텐션에 들어가기 직전 입력값으로 중심점 배정을 미리 확정**하도록 학습·검증되어 있다.
- 따라서 GPU가 이번 층 어텐션을 시작하는 **바로 그 순간**, CPU는 이미 확정된 중심점 번호표로 **`A3V4` 계획 생성 + GPU 전송을 어텐션과 나란히 실행**할 수 있다.

```text
시간 흐름 ──▶  [어텐션 직전 입력]
                   ├── GPU      : ███████████████████ 1층 어텐션 실행 (3.24 ~ 13.30 ms) ███████████████████ ──▶ [1층 FFN: 확장(gate·up) → 축소(down) 즉시 시작!]
                   └── CPU→GPU  : ███ A3V4 계획 + 번호표 전송 (1.41 ~ 2.09 ms) ███ ──▶ (이미 준비 완료 · 노출 지연 0.000 ms!)
```

**실제 RTX 4060 `d = 4,096` 어텐션 중첩 실측표 (`CH2_M32_B1B2_r9`):**

| 배치 크기 `B` | `A3V4` 4층 합 | `A3V4` 최악 1층 (`L1`) | CPU→GPU 전송 (`4층`, 크기) | 최악 1층 `계획 + 전송` | `d = 4,096` 실제 1층 어텐션 | **어텐션 노출 지연** | **여유 배수** |
|---:|---:|---:|---:|---:|---:|---:|---:|
| **`512`** | `1.50 ms` | `1.12 ms` | `1.17 ms` (`1.1 MB`) | **`1.41 ms`** | **`3.241 ms`** | **`0.000 ms`** | **`2.3×` 여유** |
| **`1,024`** | `1.49 ms` | `1.36 ms` | `1.24 ms` (`1.8 MB`) | **`1.67 ms`** | **`6.184 ms`** | **`0.000 ms`** | **`3.7×` 여유** |
| **`2,048`** | `2.83 ms` | `1.81 ms` | `1.14 ms` (`3.3 MB`) | **`2.09 ms`** | **`13.299 ms`** | **`0.000 ms`** | **`6.4×` 여유** |

직접 구현해 검증해 보았으나 두 가지 정적 방식 모두 실측에서 탈락했다.

## 2단계 · FFN 1단계(확장 · `gate·up`) 커널 — 왜 비격자로 행 짝을 바꿔도 충돌(`atomicAdd`)이 `0`인가?

어텐션이 끝나면 GPU는 방금 도착한 번호표를 들고 **FFN 1단계**(확장 · `gate·up`)를 시작한다. 먼저 FFN 한 층의 두 행렬곱이 어떻게 이어지는지 2줄로 짚고 가자.

- **FFN 1단계 (확장 · `gate·up`, `d차원 → 뉴런`):** `h = SiLU(X × W_gate) ⊙ (X × W_up)` → 결과 표 `h`의 크기 = **`토큰 B명 × 뉴런 4,096개`** *(3번 문서의 `6 × 8` 표가 바로 이 1단계 결과 표 `h`다!)*
- **FFN 2단계 (축소 · `down`, `뉴런 → d차원`):** `y = h × W_down` → `4,096`개 뉴런 값을 **전부 더해** 원래 `d`차원 출력으로 복귀!

### ① 작은 숫자 행렬곱으로 보는 FFN 1단계 실행 (`2차원 → 4뉴런`, `h = X × W`)

실제로는 `W_gate`와 `W_up` 두 행렬을 나란히 곱해 `SiLU`로 합치지만, 행렬곱 방향은 아래 **`h = X × W`와** 완전히 같다. 입력 `X`(`4토큰 × 2차원`)는 빈칸 없이 꽉 차 있고, **출력 `h`(`4토큰 × 4뉴런`)에서 필요한 칸만 비격자 타일 2개**(**틀 ① = `{T1, T2} × (N1, N2)`**, **틀 ② = `{T2, T3} × (N3, N4)`**)로 골라 계산한다.

| 왼쪽 입력 `X` (`4토큰 × 2차원`) | `1차원` | `2차원` | 　 | 오른쪽 가중치 `W` (`2차원 × 4뉴런`) | `N1` | `N2` | `N3` | `N4` |
|---|:---:|:---:|:---:|---|:---:|:---:|:---:|:---:|
| **`T1`** | `2` | `1` | | `1차원` | `1` | `2` | `1` | `2` |
| **`T2`** *(틀 ①·② 양쪽 걸침!)* | `1` | `2` | | `2차원` | `1` | `0` | `2` | `1` |
| **`T3`** | `1` | `0` | | | | | | |
| **`T4`** | `1` | `1` | | | | | | |

이제 **GPU 팀 1**(`틀 ①` 담당)과 **GPU 팀 2**(`틀 ②` 담당)가 동시에 계산해 보자. 두 팀 모두 `T2`의 입력 `[1, 2]`를 **통째로 읽되, 서로 다른 뉴런 열**과 곱한다.

| GPU 작업 팀 | 맡은 타일 구간 | 실제 행렬곱 연산 과정 (`T2` 줄 중심) | 기록하는 출력 방 |
|---|---|---|---|
| **GPU 팀 1** | **틀 ①** (`{T1, T2} × (N1, N2)`) | · `h[T1, N1] = 2×1+1×1 =` **`3`**, `h[T1, N2] = 2×2+1×0 =` **`4`**<br>· **`h[T2, N1] = 1×1+2×1 = 3`**, **`h[T2, N2] = 1×2+2×0 = 2`** | **`(T2, N1)` · `(T2, N2)` 방에만** 단독 기록! |
| **GPU 팀 2** | **틀 ②** (`{T2, T3} × (N3, N4)`) | · **`h[T2, N3] = 1×1+2×2 = 5`**, **`h[T2, N4] = 1×2+2×1 = 4`**<br>· `h[T3, N3] = 1×1+0×2 =` **`1`**, `h[T3, N4] = 1×2+0×1 =` **`2`** | **`(T2, N3)` · `(T2, N4)` 방에만** 단독 기록! |

**완성된 FFN 1단계 결과 표 `h = X × W` (`4토큰 × 4뉴런`):**

| 1단계 결과 표 `h` | `N1` 방 | `N2` 방 | `N3` 방 | `N4` 방 |
|---|:---:|:---:|:---:|:---:|
| **`T1`** | **`3`** *(팀 1 단독)* | **`4`** *(팀 1 단독)* | `0` *(계산 안 함)* | `0` *(계산 안 함)* |
| **`T2`** *(양쪽 걸침!)* | **`3`** *(팀 1 단독)* | **`2`** *(팀 1 단독)* | **`5`** *(팀 2 단독)* | **`4`** *(팀 2 단독)* |
| **`T3`** | `0` *(계산 안 함)* | `0` *(계산 안 함)* | **`1`** *(팀 2 단독)* | **`2`** *(팀 2 단독)* |
| **`T4`** | `0` *(계산 안 함)* | `0` *(계산 안 함)* | `0` *(계산 안 함)* | `0` *(계산 안 함)* |

- **충돌 `0` (`atomicAdd = 0`)!** `T2`가 두 틀에 동시에 들어갔어도 **각 칸의 내적 덧셈이 한 팀 안에서 끝까지 완결**되고, GPU 팀 1은 `N1·N2` 방(`3, 2`), GPU 팀 2는 `N3·N4` 방(`5, 4`)으로 **아예 다른 방에만 쓰기 때문**이다. 3번 문서에서 모든 `1` 칸을 중복 없이 딱 1번씩만 덮도록 타일을 짰으므로 충돌 자체가 구조적으로 `0건`이다.
- *(참고: "희소 행렬곱에서 행 짝을 타일마다 바꾸면 `atomicAdd` 충돌이 나지 않나?"라는 질문이 자주 나오지만, 그 충돌은 왼쪽 입력이 희소할 때 생긴다. FFN 1단계는 오른쪽 결과 `h`가 희소해 충돌이 `0`이며, 바로 아래 FFN 2단계에서 비로소 왼쪽 입력이 희소해진다!)*

### ② 실제 FFN 1단계 커널이 챙기는 2가지 깔끔한 연결 트릭 (6명 예시로 한눈에 보기)

FFN 1단계(확장 · `gate·up`) 커널이 실제로 계산을 마치고 결과를 적을 때는 **두 가지 영리한 규칙**을 동시에 써서, 바로 이어지는 FFN 2단계(축소 · `down`)를 위한 준비까지 공짜로 끝내 버린다.

1. **기록 허용 도장(쓰기 마스크)으로 `×0` 방 보호:** FFN 1단계 시작 직전에 결과 표 `h`를 `0`으로 한 번 비워 둔다 *(4층 합 `0.025 ~ 0.078 ms`, 전체 시간의 `0.5%`)*. 타일 안에서 `×0` 빈칸이 텐서 코어로 강제 계산되더라도, **도장이 찍힌 `1` 칸만 결과 표에 적고 빈칸 `×0`은 아예 덮어쓰지 않아**(`0` 유지) 충돌과 오염을 원천 차단한다.
2. **읽을 땐 뒤죽박죽 원래 줄, 적을 땐 이미 가지런히 정렬된 줄:** FFN 1단계 커널은 입력은 원래 도착한 줄에서 읽어 계산하지만, 결과 표 `h`에 적을 때는 **1단계에서 정리해 둔 닮은 중심점 순서(`A → B → C → D`) 줄에 곧바로 기록**한다.

| 입력 메모리 (뒤죽박죽 도착한 원래 줄) | FFN 1단계(확장) 커널 실행 중 | 1단계 결과 표 `h` (저장할 때 이미 가지런히 정렬!) |
|---|---|---|
| `0번 줄`: `T5` (`C`)<br>`1번 줄`: `T1` (`A`)<br>`2번 줄`: `T6` (`D`)<br>`3번 줄`: `T2` (`A`)<br>`4번 줄`: `T4` (`B`)<br>`5번 줄`: `T3` (`A`) | · 원래 줄에서 입력을 읽어 계산<br>· **`1` 도장 찍힌 칸만** 정렬된 줄에 기록<br>*(빈칸 `×0`은 덮어쓰지 않아 `0` 유지)* | `0번 줄`: **`T1` (`A`)** ◀ 2단계 묶음 1 (`A + A`)<br>`1번 줄`: **`T2` (`A`)** ◀ 2단계 묶음 1 (`A + A`)<br>`2번 줄`: **`T3` (`A`)** ◀ 2단계 묶음 2 (`A + B`)<br>`3번 줄`: **`T4` (`B`)** ◀ 2단계 묶음 2 (`A + B`)<br>`4번 줄`: **`T5` (`C`)** ◀ 2단계 묶음 3 (`C + D`)<br>`5번 줄`: **`T6` (`D`)** ◀ 2단계 묶음 3 (`C + D`) |

- 덕분에 바로 이어지는 **FFN 2단계**(축소 · `down`)로 넘어갈 때 토큰 행을 다시 정렬해 복사하는 비용이 **0**이다!

<details>
<summary><b>참고 · FFN 1단계(확장) 커널이 번호표 gather를 끼고도 <code>cuBLAS</code>의 <code>90.3%</code> 효율을 내는 이유</b></summary>

1. **긴 연속 막대기 로드 (2번 문서 연결):** 토큰 1줄과 뉴런 1줄은 숫자 1알이 아니라 **`2 ~ 8 KB`(캐시라인 `16 ~ 64`박스)짜리 긴 연속 막대기**다. 번호표 1번만 보고 나면 깊이 방향(`d`)을 `32`개 숫자(`64바이트`)씩 슬라이스로 썰어 버리는 바이트 `0%`로 쭉 읽어 온다.
2. **구역 순서 실행 (`Strip512`):** 3번 문서 5단계대로 8개 구역(`512`열 = `8 MB`씩) 순서대로 실행하므로, 가중치가 느린 DRAM이 아니라 빠른 **L2 캐시에 상주**한 채로 비격자 타일들이 긁어 간다.
3. **`v4` 커널 하드웨어 튜닝:** 가중치와 입력 양쪽에 `L1 + L2` 동시 캐싱(`cp.async.ca`)을 켜고, 공유 메모리(SMEM) 사용량을 `26.2 KB → 21.4 KB`로 줄여 **SM당 동시 실행 팀 수**(`4 CTAs/SM`)를 최대로 잠갔으며, 구역 내 타일을 열 번호 순으로 2차 정렬해 L1 적중률을 높였다. 그 결과 밀집 `64×32` 기준 **`cuBLAS`의 `90.3%`** (`d = 4,096`, `19.26 vs 21.32 TF`) · **`89.1%`** (`d = 1,024`, `18.43 vs 20.68 TF`)를 달성했다.

</details>

## 3단계 · FFN 2단계(축소 · `down`) 커널(열 압축 → 합산 + 잔차) — 왜 1단계와 따로 푸나?

이제 방금 FFN 1단계(확장 · `gate·up`)가 가지런히 채워 둔 결과 표 `h`를 가지고 **FFN 2단계(축소 · `down`)**(`y = h × W_down + 잔차`)를 계산할 차례다.

### ① 왜 1단계의 비격자 타일을 2단계(`y = h × W_down`)에 그대로 못 쓰나?

1단계(`d차원 → 뉴런 확장`, `SDDMM` 형태)와 2단계(`뉴런 → d차원 축소`, `SpMM` 형태)는 겉보기엔 똑같은 행렬곱 같지만 성격이 정반대다. 2단계에서는 방금 1단계가 만든 **똑같은 결과 표 `h`**(`4토큰 × 4뉴런`)가 왼쪽 입력으로 들어가, **원래 `2차원`으로 복귀(축소)하기 위해 한 토큰이 켠 뉴런 값을 전부 더해야** 한다.

| 왼쪽 입력 `h` *(방금 1단계 결과!)* | `N1` | `N2` | `N3` | `N4` | 　 | 오른쪽 가중치 `W_down` | `1차원` | `2차원` |
|---|:---:|:---:|:---:|:---:|:---:|---|:---:|:---:|
| **`T1`** | **`3`** *(틀①)* | **`4`** *(틀①)* | `0` | `0` | | `N1` | `1` | `2` |
| **`T2`** *(양쪽 걸침!)* | **`3`** *(틀①)* | **`2`** *(틀①)* | **`5`** *(틀②)* | **`4`** *(틀②)* | | `N2` | `2` | `1` |
| **`T3`** | `0` | `0` | **`1`** *(틀②)* | **`2`** *(틀②)* | | `N3` | `1` | `0` |
| **`T4`** | `0` | `0` | `0` | `0` | | `N4` | `2` | `1` |

만약 1단계처럼 **틀 ①**(`GPU 팀 1`)과 **틀 ②**(`GPU 팀 2`)로 뉴런 열을 쪼개서 `y = h × W_down`을 계산하면 어떻게 될까?

| GPU 작업 팀 | 맡은 타일 구간 | 실제 행렬곱 연산 과정 (`T2` 줄 중심) | 기록해야 하는 출력 방 |
|---|---|---|---|
| **GPU 팀 1** | **틀 ①** (`{T1, T2} × (N1, N2)`) | · `T1`: `1차원 = 3×1+4×2 =` **`11`**, `2차원 = 3×2+4×1 =` **`10`**<br>· **`T2`(앞 절반):** `1차원 = 3×1+2×2 =` **`7`**, `2차원 = 3×2+2×1 =` **`8`** | **`y[T2, 1차원]`에 `+7`**, **`y[T2, 2차원]`에 `+8`** |
| **GPU 팀 2** | **틀 ②** (`{T2, T3} × (N3, N4)`) | · **`T2`(뒤 절반):** `1차원 = 5×1+4×2 =` **`13`**, `2차원 = 5×0+4×1 =` **`4`**<br>· `T3`: `1차원 = 1×1+2×2 =` **`5`**, `2차원 = 1×0+2×1 =` **`2`** | **`y[T2, 1차원]`에 `+13`**, **`y[T2, 2차원]`에 `+4`** |

**완성해야 할 FFN 2단계 결과 표 `y = h × W_down` (`4토큰 × 2차원`):**

| 2단계 결과 표 `y` | `1차원` 방 | `2차원` 방 |
|---|:---:|:---:|
| **`T1`** | **`11`** *(팀 1 단독)* | **`10`** *(팀 1 단독)* |
| **`T2`** *(충돌 발생!)* | **`7`** *(팀 1)* + **`13`** *(팀 2)* = **`20`** *(충돌!)* | **`8`** *(팀 1)* + **`4`** *(팀 2)* = **`12`** *(충돌!)* |
| **`T3`** | **`5`** *(팀 2 단독)* | **`2`** *(팀 2 단독)* |
| **`T4`** | `0` *(계산 안 함)* | `0` *(계산 안 함)* |

- **충돌 발생!** 1단계와 달리 2단계는 뉴런 `N1 ~ N4`를 **원래 차원(`2차원`)으로 복귀(축소)하기 위해 전부 한 방에 더해야 하는 단계**다. 그래서 1단계처럼 뉴런 열을 여러 팀으로 쪼개면 **GPU 팀 1과 GPU 팀 2가 똑같은 `y[T2, 1차원]` · `y[T2, 2차원]` 방에 동시에 더하려다 `atomicAdd` 충돌**이 터진다.
- **해결 원칙:** 그래서 FFN 2단계에서는 뉴런 열을 여러 팀으로 쪼개지 않고, **한 GPU 팀이 맡은 토큰 묶음의 모든 활성 뉴런을 처음부터 끝까지 자기 안에서 다 더해(`7 + 13 = 20`) `y` 방에 딱 1번만 기록**한다!

### ② 우리 해법: 3번 문서의 `6 × 8` 예시로 보는 묶음별 활성 열 압축 + 전담 합산

방금 앞 단계(FFN 1단계 · 확장)가 이미 결과 표 `h`를 **닮은 중심점 순서**(`A → B → C → D`)대로 가지런히 저장해 두었다. 이제 FFN 2단계(축소 · `down`)는 이 정렬된 표를 위에서부터 **연속된 `TM`명씩 토큰 묶음**(이 예시에서는 `2`명씩 3묶음)으로 자른다.

| 2단계 토큰 묶음 (이미 정렬된 결과 표 `h`) | 이 묶음의 `h` 값 (`N1 ~ N8`) | **활성 열 압축** 결과 (**합집합 열만 쏙 추출!**) | 실제 계산 열 비율 |
|---|:---:|---|---:|
| **묶음 1**<br>`T1` (`A`)<br>`T2` (`A`) | `T1`: `1 1 1 0 1 0 0 0`<br>`T2`: `1 1 1 0 1 0 0 0` | **활성 열 `{N1, N2, N3, N5}`** (`8열 → 4열`로 압축!)<br>`T1`: `[a1, a2, a3, a5]`<br>`T2`: `[a1, a2, a3, a5]` | **`4 / 8` (`50%`)**<br>*(빈칸 `0`!)* |
| **묶음 2**<br>`T3` (`A`)<br>`T4` (`B`, 같은 가족) | `T3`: `1 1 1 0 1 0 0 0`<br>`T4`: `0 0 1 1 1 0 1 0` | **활성 열 `{N1, N2, N3, N4, N5, N7}`** (`8열 → 6열`로 압축!)<br>`T3`: `[a1, a2, a3, 0, a5, 0]`<br>`T4`: `[0, 0, a3, a4, a5, a7]` | `6 / 8` (`75%`)<br>*(안 쓰는 `N6, N8` 제외)* |
| **묶음 3**<br>`T5` (`C`)<br>`T6` (`D`, 이웃) | `T5`: `0 0 0 1 0 1 1 1`<br>`T6`: `1 1 0 0 0 0 0 1` | **활성 열 `{N1, N2, N4, N6, N7, N8}`** (`8열 → 6열`로 압축!)<br>`T5`: `[0, 0, a4, a6, a7, a8]`<br>`T6`: `[a1, a2, 0, 0, 0, a8]` | `6 / 8` (`75%`)<br>*(안 쓰는 `N3, N5` 제외)* |

**실제 `CH2` 스케일에서 터지는 폭발적 시너지:**
- 앞 3층 중심점이 32개뿐이라 `B = 2,048`에서는 중심점 하나당 평균 **64명**이 모인다. 그래서 `32`명씩 묶음을 자르면 대부분이 위 **묶음 1**처럼 **100% 같은 중심점 토큰만으로 꽉 차고**, 경계 묶음조차 같은 가족 이웃만 살짝 섞인다.
- 덕분에 2단계 묶음의 평균 합집합 비율이 **`22.7%` (`B = 512`) → `18.6%` (`B = 1,024`) → `16.1%` (`B = 2,048`) 수준**까지 떨어져, 원래 평균 켜는 뉴런(`13.52%`)에 거의 바짝 붙는다!

**실제 GPU 2단계 실행 순서 (`atomicAdd = 0`):**
1. **초고속 활성 열 압축 (`pack_h_v4`, 층당 `0.012 ms`):** 각 묶음에서 합집합에 들어간 열만 2D 벡터 복사로 쏙쏙 뽑아 빈틈없는 작은 표로 모은다 *(기존 `v3` 대비 5~7배 빨라져 전체 시간의 1% 미만)*.
2. **FFN 2단계(축소 · `down + 잔차`) 커널 융합 실행:** **한 GPU 작업 팀이 한 묶음(`TM`명)을 처음부터 끝까지 전담**한다. 압축된 작은 표와 대응하는 `W_down` 줄만 읽어 자기 내부 레지스터 안에서 모든 활성 뉴런 합산을 끝까지 마친 뒤, **각 토큰의 원래 도착 자리(`T1 → 1번 줄`, `T5 → 0번 줄` 등)의 잔차 출력에 딱 1번만 더하고 종료**한다.
   - **다른 GPU 작업 팀과 겹치는 출력 토큰이 0명이므로 2단계 역시 `atomicAdd = 0`이다!**

### ③ 층별 자동 묶음 크기 선택 (`1~3층 32명`, `4층 16명`)
- 한 묶음 인원(`TM`)이 많으면 `W_down` 가중치를 여러 토큰이 오래 돌려 써서 텐서 코어 효율이 높고(`32`명 묶음 밀집 효율 **`93.1%`** of `cuBLAS`), 적으면 서로 다른 중심점이 덜 섞여 합집합 열 수가 줄어든다(`16`명 묶음 밀집 효율 **`68.5%`**).
- `A3V4`는 매 배치마다 각 층의 실제 합집합과 RTX 4060 실측 단가를 자동 비교해 유리한 묶음 크기를 고른다 → 실제 `CH2`에서는 **1~3층은 `32`명**, 256개 중심점에 `0.8%`만 켜는 **4층은 `16`명이** 자동 선택된다.

<details>
<summary><b>참고 · 왜 <code>8</code>명 묶음(<code>TM = 8</code>)으로 더 잘게 쪼개지 않고 버렸나? (실리콘 실측 반증)</b></summary>

- 이론만 보면 `8`명으로 더 작게 자르면 합집합이 더 줄 것 같지만, 실제 RTX 4060에서 `k32` 슬라이스당 실행 시간을 재 보니 `TM = 32`는 **`0.433 µs`** · `TM = 16`은 **`0.294 µs`** · `TM = 8`은 **`0.256 µs`였다.**
- `TM = 8`은 묶음 크기가 `1/4`로 줄면서 GPU 작업 팀 수가 4배로 폭증해 `W_down`을 L2/L1에서 반복 재로드하게 되고, 밀집 효율이 **`27.8%`까지** 추락했다.
- 실측 단가 계산상 `TM = 16`이 `TM = 32`를 이기려면 합집합이 **`32%` 이상** 줄어야 하며(4층만 충족), `TM = 8`은 전 층에서 오히려 느려져 실측 탈락했다.

</details>

## 4단계 · 최종 RTX 4060 E2E 실측 & 솔직한 경계선 (`CH2 + v4 + A3V4`)

### ① 큰 모델 (`d = 4,096`, `96 MB/층 > L2 32 MB`) 4층 합계 동일 세션 실측

| 배치 `B` | Base (`cuBLAS`) | `0-Mask` | **우리 어텐션 중첩 E2E** | 우리 직렬 E2E *(중첩 0%)* | `확장 + 축소` 분해 (`ms`) | 전체 FFN 연산량 | `DRAM` 읽는 양 | `fp32` 최대 오차 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| **`512`** | `9.580 ms` (`1.00×`) | `1.02×` | **`3.113 ms` (`3.08×`)** | `5.779 ms` (`1.66×`) | `2.041 + 1.071` | **`20.4%`** | **`64.2%`** | `2.21e-3` |
| **`1,024`** | `19.071 ms` (`1.00×`) | `1.02×` | **`4.658 ms` (`4.09×`)** | `7.393 ms` (`2.58×`) | `2.874 + 1.783` | **`17.0%`** | **`64.2%`** | `1.86e-3` |
| **`2,048`** | `38.243 ms` (`1.00×`) | `1.03×` | **`8.373 ms` (`4.57×`)** | **`12.347 ms` (`3.10×`)** | `5.087 + 3.286` | **`15.6%`** | **`64.5%`** | `2.06e-3` |

- **1단계(확장)와 2단계(축소) 균형 가속:** `B = 2,048` 기준 FFN 1단계(`5.09 ms`)와 FFN 2단계(`3.29 ms`)가 각각 전체의 `60.8%` · `39.2%`로 원래 FFN 연산 비율(`2:1`)에 가깝게 양쪽 모두 균형 있게 줄어 **`4.57×`를** 달성했다 *(중첩 없이 CPU 계획+전송을 직렬 합산해도 **`3.10×`**)*.
- **수치 정합성:** 전 구간에서 `PyTorch fp32` 정답 대비 최대 상대 오차가 **`1.72e-3 ~ 2.21e-3`**(허용 기준 `0.02`의 약 `1/10`)이며, `1* = 0%` 덕분에 10,000장 시험 정확도는 `B = 1 / 512 / 2,048` 모두 완전히 똑같은 **`90.81%`**(묶기 하락 `0.00%p`)다.

### ② 층별 분해 (`B = 2,048`, `d = 4,096` — 저·중·고 밀도 전 구간 가속)

| 층 | 평균 켜는 `K` | Base (`ms`) | **우리 최종 (`ms` / 배수)** | 1단계 채움률 | 2단계 합집합 (`TM`) | `DRAM` 읽는 양 | 총 틀 수 |
|:---:|---:|---:|---:|---:|---:|---:|---:|
| **1층** | `22.07%` | `8.987` | **`3.086` (`2.91×`)** | **`89.4%`** | `25.8%` (`32`) | **`82.9%`** | `1,508` |
| **2층** | `21.67%` | `9.318` | **`2.967` (`3.14×`)** | **`88.3%`** | `25.4%` (`32`) | **`88.1%`** | `1,536` |
| **3층** | `9.55%` | `9.373` | **`1.613` (`5.81×`)** | `84.1%` | `11.8%` (`32`) | **`72.1%`** | `876` |
| **4층** | `0.80%` | `9.243` | **`0.607` (`15.22×`)** | `60.4%` | `1.3%` (`16`) | **`14.8%`** | `183` |

- 가장 무거운 **1·2층(`K ≈ 22%`)에서도 `88.3 ~ 89.4%` 타일 채움률과 `2.91 ~ 3.14×` 가속**을 뽑아내고, 3층 **`5.81×`** · 4층 **`15.22×`까지** 전 밀도 구간에서 고르게 가속된다. 또한 1~3층에서 모든 중심점이 쓰지 않는 가중치 열이 영구 제거되어 **4층 평균 `DRAM` 읽기 양도 `64.5%`로** 줄었다.
- **위 표의 '1단계 채움률 (타일 채움률)'이란?** GPU 텐서 코어에 집어넣은 네모 틀(타일) 전체 칸 중에서, **헛계산(`×0`)이 아니라 진짜 필요한 유효 뉴런(`1`)이 채워져 있는 비율**이다 *(항상 `채움률 + ×0 비중 = 100%`이며, `B = 2,048` 4층 평균 **`87.4%`** = 버리는 `×0`은 `12.6%`뿐)*.
- **위 표의 '1단계 채움률 (타일 채움률)'이란?** GPU 텐서 코어에 집어넣은 네모 틀(타일) 전체 칸 중에서, **헛계산(`×0`)이 아니라 진짜 필요한 유효 뉴런(`1`)이 채워져 있는 비율**이다 *(항상 `채움률 + ×0 비중 = 100%`이며, `B = 2,048` 4층 평균 **`87.4%`** = 버리는 `×0`은 `12.6%`뿐)*.

$$\text{타일 채움률} = \frac{\text{틀 안의 진짜 필요한 } 1 \text{ 칸 수}}{\text{틀 전체 칸 수 (진짜 } 1 + \text{ 헛계산 } \times 0\text{)}}$$

- **위 표의 '2단계 합집합'이란?** FFN 2단계(축소 · `down`)에서 **한 GPU 작업 팀이 맡은 토큰 묶음(`32`명 또는 `16`명) 안에 있는 토큰들 중, 단 1명이라도 켠 뉴런을 전부 모은 비율**이다 *(2단계는 충돌을 없애려고 묶음 하나를 작은 행렬곱 1번으로 통째로 돌리므로, 이 합집합 비율이 곧 2단계 실제 연산량이다)*.
  - **8뉴런 예시:** 같은 중심점 `A`끼리 묶인 `T1 + T2`는 둘 다 `{N1, N2, N3, N5}`만 써서 합집합이 **`4 / 8 = 50%`** (버리는 칸 `0`개)이고, 서로 다른 중심점이 섞인 `T3(A) + T4(B)`는 `{N1, N2, N3, N4, N5, N7}`로 **`6 / 8 = 75%`가** 된다.
  - **실제 의미 (`4층 평균 16.1%`):** 원래 토큰 1명이 평균 `13.52%`의 뉴런을 켜는데, 같은 중심점·가족끼리 나란히 모아 둔 덕분에 **`32`명씩 묶어서 합집합을 내도 `100%`로 안 터지고 4층 평균 `16.1%`만 계산하면 끝난다** *(1층 `25.8%`, 2층 `25.4%`, 3층 `11.8%`, 4층 `1.3%`)*.

$$\text{타일 채움률} = \frac{\text{틀 안의 진짜 필요한 } 1 \text{ 칸 수}}{\text{틀 전체 칸 수 (진짜 } 1 + \text{ 헛계산 } \times 0\text{)}}$$

- **위 표의 '2단계 합집합'이란?** FFN 2단계(축소 · `down`)에서 **한 GPU 작업 팀이 맡은 토큰 묶음(`32`명 또는 `16`명) 안에 있는 토큰들 중, 단 1명이라도 켠 뉴런을 전부 모은 비율**이다 *(2단계는 충돌을 없애려고 묶음 하나를 작은 행렬곱 1번으로 통째로 돌리므로, 이 합집합 비율이 곧 2단계 실제 연산량이다)*.
  - **8뉴런 예시:** 같은 중심점 `A`끼리 묶인 `T1 + T2`는 둘 다 `{N1, N2, N3, N5}`만 써서 합집합이 **`4 / 8 = 50%`** (버리는 칸 `0`개)이고, 서로 다른 중심점이 섞인 `T3(A) + T4(B)`는 `{N1, N2, N3, N4, N5, N7}`로 **`6 / 8 = 75%`가** 된다.
  - **실제 의미 (`4층 평균 16.1%`):** 원래 토큰 1명이 평균 `13.52%`의 뉴런을 켜는데, 같은 중심점·가족끼리 나란히 모아 둔 덕분에 **`32`명씩 묶어서 합집합을 내도 `100%`로 안 터지고 4층 평균 `16.1%`만 계산하면 끝난다** *(1층 `25.8%`, 2층 `25.4%`, 3층 `11.8%`, 4층 `1.3%`)*.

### ③ 작은 모델 (`d = 1,024`, 실제 학습 `CH2` 가중치) & 어텐션 중첩의 솔직한 경계선

| 배치 `B` | Base (`cuBLAS`) | **우리 GPU FFN** | `확장 + 축소` 분해 (`ms`) | `d = 1,024` 1층 어텐션 | 우리 직렬 E2E *(중첩 0%)* | `fp32` 최대 오차 |
|---:|---:|---:|---:|---:|---:|---:|
| **`512`** | `2.476 ms` | **`0.825 ms` (`3.00×`)** | `0.514 + 0.311` | `0.231 ms` | `3.451 ms` (`0.72×`) | `1.72e-3` |
| **`1,024`** | `4.820 ms` | **`1.260 ms` (`3.83×`)** | `0.763 + 0.497` | `0.519 ms` | **`3.892 ms` (`1.24×`)** | `1.78e-3` |
| **`2,048`** | `9.873 ms` | **`2.285 ms` (`4.32×`)** | `1.340 + 0.945` | `1.299 ms` | **`6.261 ms` (`1.58×`)** | `1.78e-3` |

- **정직한 경계선:** `d = 1,024`는 실제 1층 어텐션 자체가 `0.23 ~ 1.30 ms`로 매우 짧아 CPU `A3V4` 계획 + 전송 시간을 어텐션 뒤에 전부 숨기지 못한다. **어텐션 `0.000 ms` 완전 은폐는 실제 대형 LLM 크기(`d ≥ 4,096`)에서 성립**한다.
- 다만 `CH2`는 전체 타일 수가 작고 디스패치가 빨라, 중첩을 전혀 쓰지 않는 **직렬 합산 E2E**에서도 `d = 1,024` `B = 1,024 / 2,048`에서 **`1.24× / 1.58×`** 순가속을 달성했다.
